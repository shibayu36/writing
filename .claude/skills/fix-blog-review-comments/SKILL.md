# fix-blog-review-comments

直前の会話に含まれるブログ記事のレビュー指摘を精査し、妥当な指摘のみ修正を行う。

## 動作フロー

1. 直前の会話からレビュー指摘を特定・一覧化する
2. 各指摘の妥当性を評価する
   - 記事の意図・想定読者との整合性
   - `WRITING.md` / `WRITING_GUIDELINE.md` / `core-message-writing` の方針との整合性
   - 指摘同士が矛盾する場合は、記事の意図に照らしてどちらを優先するか判断する
3. 妥当と判断した指摘のみ記事を修正する
4. 修正完了後、`npm exec -- textlint --fix <記事ファイル>` を実行する。自動修正で解消しなかったlintエラーは手動で修正する
5. 最終サマリーを出力する

## 妥当性評価の基準

- レビュアーの指摘を鵜呑みにせず、記事の意図・想定読者・各ガイドラインとの整合性を独自に判断する
- 対応しない場合は、レビュアーが納得できる理由を明記する
- 修正によって新たな問題（文体の乱れ、事実誤認など）が発生しないか確認する

## 最終サマリーの形式

修正完了後、以下の形式でサマリーを出力すること。
サマリーの目的は「修正判断が適切だったかをユーザーがダブルチェックできること」であり、元の指摘内容・判断根拠を省略しすぎないこと。

### 記載ルール

各指摘について以下の3点を必ず記載する：

1. **見出し**：「レビュアー識別子: 指摘の要点」の形式
   - レビュアー識別子は会話中のレビュー結果に記載された名前・番号をそのまま使う（例：core-message-reviewer #1, style-reviewer #2）
   - 複数レビュアーが同じ指摘をしている場合は「core-message-reviewer #1 / style-reviewer #2」のようにスラッシュで併記する
2. **指摘内容**：レビュアーが何を問題視したか。元のレビューコメントの趣旨がわかる程度に具体的に書く
3. **修正内容 or 対応しない理由**：何をどう変えたか、またはなぜ対応不要と判断したかの根拠

### 出力テンプレート

```markdown
## レビュー対応サマリー

### 対応した指摘

#### core-message-reviewer #1: 冒頭が一般論の枕詞から始まっている
- **指摘内容**: 冒頭が「近年、AIエージェントの活用が広がっている」という一般論から始まっており、コアメッセージが立ち上がるまでに1段落かかっている
- **修正内容**: 冒頭を一般論の枕詞から本題（readonly configurationを作った動機）に差し替え

#### style-reviewer #2: 見出しが抽象的
- **指摘内容**: 「### 工夫した点」という見出しが抽象的で、内容が想像できない
- **修正内容**: 見出しを「### readonlyロールでも調査できる範囲を広げる」に変更

### 対応しなかった指摘

#### tech-accuracy-reviewer #1: configurationの命名規則
- **指摘内容**: gcloud configurationの命名に公式のnamingガイドを使うべきでは
- **対応しない理由**: 公式ドキュメントに命名規則の明確な推奨は無く、好みの範囲の指摘であるため対応しない
```
