最近はClaude Codeなどのコーディングエージェントにgcloudやbqコマンドを使わせて、インフラの状況確認やBigQueryへのクエリ実行といったGCP上の調査を任せることが増えてきた。しかしインフラのリソース変更をできる権限のままAIにコマンドを実行させると、調査しか頼んでいないのに、AIの誤操作で意図せずインフラに影響が出る可能性があり、これは怖い。

AIに書き込み操作をさせたくないという課題意識は、以前[ghコマンド用にreadonlyラッパーを作った](https://blog.shibayu36.org/entry/2026/03/09/173000)時と同じだ。今回はそのGCP版として、readonly権限しか持たないgcloud configurationを用意した。そのやり方をメモしておく。

### 方針: readonlyのService Accountを作り、impersonateする専用configurationを用意する

構成は以下のとおり。

```
自分のGoogleアカウント
  ↓ impersonate
readonly用Service Account
  └─ roles/viewer
```

readonly系のロールだけを付与したService Accountを作り、自分のアカウントからservice account impersonationでそのSAとして振る舞う。このimpersonation設定は専用のgcloud configurationとして分離しておく。こうすると`gcloud config configurations activate`一発で、普段の権限とreadonly権限を切り替えられる。

### 構築手順: SA作成 → ロール付与 → impersonate許可 → configuration作成

以下、プロジェクトIDを`my-project`、自分のアカウントを`shibayu36@example.com`として進める。

まずreadonly用のService Accountを作る。

```bash
gcloud iam service-accounts create my-readonly \
  --project=my-project \
  --display-name="Readonly CLI"
```

次に、このSAに対象プロジェクトの`roles/viewer`を付与する。

```bash
gcloud projects add-iam-policy-binding my-project \
  --member="serviceAccount:my-readonly@my-project.iam.gserviceaccount.com" \
  --role="roles/viewer"
```

試した限りでは、`roles/viewer`だけでリソースの閲覧に加えてBigQueryのクエリ実行やテーブル参照までできた。調査対象のプロジェクトが複数あるなら、それぞれのプロジェクトに付与する。

続いて、自分のアカウントがこのSAにimpersonateできるように権限を付与する。

```bash
gcloud iam service-accounts add-iam-policy-binding \
  my-readonly@my-project.iam.gserviceaccount.com \
  --project=my-project \
  --member="user:shibayu36@example.com" \
  --role="roles/iam.serviceAccountTokenCreator"
```

最後に、impersonation設定込みのgcloud configurationを作る。`configurations create`すると同時にそのconfigurationがアクティブになるので、続く`config set`はこのconfigurationに対して行われる。

```bash
gcloud config configurations create my-readonly
gcloud config set account shibayu36@example.com
gcloud config set auth/impersonate_service_account my-readonly@my-project.iam.gserviceaccount.com
```

なお`project`はあえて設定していない。デフォルトプロジェクトを持たせず、コマンド実行時に毎回`--project_id`を明示する運用にすることで、意図しないプロジェクトを参照してしまう事故を防いでいる。これで準備完了。

### 使い方: 普段からreadonly configurationを使い、書き込みする時だけ戻す

自分の場合、普段の操作もほとんど閲覧しかしない。そこで基本はreadonly configurationをアクティブにしたまま過ごし、AIエージェントもその状態で動かしている。自分で書き込み操作をする時だけ、元のconfigurationへ戻す。

```bash
# 基本はreadonlyをアクティブにしておく
gcloud config configurations activate my-readonly

# この状態でClaude Codeなどを起動して調査を任せる
# 実行されるコマンドの例:
#   gcloud compute instances list --project=my-project
#   bq query --project_id=my-project --use_legacy_sql=false 'SELECT ...'

# 自分で書き込み操作をしたい時だけ通常のconfigurationに戻す
gcloud config configurations activate default
```

本当にreadonlyになっているかも検証した。この状態でBigQueryのdataset作成を試すと、ちゃんと拒否される。

```bash
bq mk --dataset "my-project:tmp_readonly_check"
# → BigQuery error in mk operation: Access Denied: Project my-project:
#    User does not have bigquery.datasets.create permission in project my-project.
```

### まとめ

readonly専用のconfigurationを1つ用意しておくだけで、AIにGCP調査を任せる時の心理的ハードルがかなり下がった。同じようにAIにGCP調査を任せたいが権限が怖いという人は試してみてほしい。

また今回の記事では全体のリソースを見れるように`roles/viewer`を付与したが、同じような仕組みで必要なリソースのみに権限を絞ることもできる。もう少し細かく制御したいなら、そうすると良いだろう。
